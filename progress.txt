## Codebase Patterns

- Namespace root is `CratisApp`; slices live under `<Module>/<Feature>/<Slice>/<Slice>.cs` (e.g.
  `Reservations/Booking/PlaceReservation/PlaceReservation.cs`, `ShiftManagement/Scheduling/CreateShift/CreateShift.cs`).
  Module-level shared concepts (`ConceptAs<T>`) sit one level up, e.g. `ShiftManagement/Scheduling/ShiftId.cs`.
- There is NO test project checked in by default (`CratisApp.Specs` was previously removed as "added
  incorrectly"). The root cause: `CratisApp.csproj` uses `Microsoft.NET.Sdk.Web`'s default `**/*.cs`
  glob, so nesting a test project's folder inside the repo root without excluding it makes the main
  project try to compile the test project's own files too (CS0579 duplicate-attribute errors). Before
  adding any files under `CratisApp.Specs/`, add to `CratisApp.csproj`:
  `<ItemGroup><Compile Remove="CratisApp.Specs/**/*.cs" /><Content Remove="CratisApp.Specs/**/*" /><None Remove="CratisApp.Specs/**/*" /></ItemGroup>`.
  Scaffold with `dotnet new xunit -n CratisApp.Specs -o CratisApp.Specs`, retarget to `net9.0`, add
  `Cratis.Specifications` / `Cratis.Specifications.XUnit` / `NSubstitute` (`Version="*"`) plus a
  `ProjectReference` to `..\CratisApp.csproj`, delete the scaffolded `UnitTest1.cs`, add a
  `GlobalUsings.cs` (`global using Cratis.Specifications;` / `global using Xunit;`), and register it
  with `dotnet sln CratisApp.sln add CratisApp.Specs/CratisApp.Specs.csproj` (never hand-edit the
  `.sln`). The specs project does NOT set `TreatWarningsAsErrors` — CS8618 nullable-field warnings on
  unassigned spec fixture fields are expected/harmless, matching the original spec files' style.
- A command field marked `"generated": true` in slice JSON is excluded from the `[Command]` record's
  parameters — it's computed in `Handle()` and only appears on the resulting event. If it's also
  `"idAttribute": true`, use the "generate-and-return" pattern: `Handle()` returns `(TId, TEvent)`,
  generating `TId.New()` internally and passing it into the event constructor too (since the modeled
  event still lists the id as one of its own fields, even though it's also the event source).
- Cross-field command validation with no event-sourced state needed (e.g. "end must be after start",
  "fromDay must not be later in the week than toDay") goes in `CommandValidator<T>` via
  `RuleFor(c => c.PropertyA).Must((command, value) => ...compare against command.PropertyB...)` /
  `.GreaterThan(command => command.OtherProperty)` — test by instantiating the validator directly in a
  spec and asserting `validator.Validate(command).IsValid`, no Chronicle/HTTP fixture needed.
- `ConceptAs<T>`, `EventSourceId`, `[Command]`, `[EventType]`, `[Key]` etc. resolve in slice `.cs` files
  with NO explicit `using` — the Cratis SDK injects its own implicit global usings. Don't add usings to
  concept/slice files just because a type looks unqualified; match the existing files (none).
- Proxy-generated `index.ts` barrels are NOT clobbered on rebuild once hand-edited — adding a second
  `export * from './XyzDialog'` line survives subsequent `dotnet build` runs.
- Read-model specs: MongoDB.Driver 3.x has NO instance `Find`/`FirstOrDefaultAsync` on
  `IMongoCollection<T>` — they're extension methods that ultimately call the interface method
  `FindAsync<TProjection>(FilterDefinition<T>, FindOptions<T,TProjection>, CancellationToken)`. To unit
  spec a `[ReadModel]` static query without a live Mongo/Chronicle instance, substitute
  `IMongoCollection<T>.FindAsync(...)` (NSubstitute) to return a substituted `IAsyncCursor<T>` whose
  `Current` yields the expected row and `MoveNextAsync` returns `true` then `false` — the query
  method's own `.Find(expr).FirstOrDefaultAsync()` call resolves through that mock correctly. No
  Testcontainers/real MongoDB needed for simple single-model queries.
- Record-level `[ReadModel][FromEvent<TEvent>]` AutoMap matches read-model properties to event
  properties **by name** (case-insensitive) — name the id property after the domain concept (e.g.
  `ShiftId`, not `Id`) when the source event already carries that field explicitly; `Id`-named
  properties only get special-cased to the raw event-source id when the event itself has no
  matching field (see `SomeModule/SomeFeature/Listing.cs`'s `Guid Id` from an event with no `Id`).
- A `ConceptAs<Guid>` concept only gets `implicit operator EventSourceId(...)` if it is meant to be
  a command's own event-source/stream key (e.g. `ShiftId`). A same-command Guid field that is just a
  foreign reference (e.g. `EmployeeId` on `AssignEmployeeToShift`) must NOT define that operator —
  Arc's `ARCCHR0002` analyzer treats every property with an implicit `EventSourceId` conversion as an
  event-source-id *candidate*, and having two on one command is a build error ("multiple event source
  id candidate properties ... does not implement ICanProvideEventSourceId"). Compare `ShiftId.cs`
  (has the operator) vs. `RestaurantId.cs`/`EmployeeId.cs` (foreign-reference ids, no operator).
- DCB business rules keyed on a single-value read model (matching the command's `[Key]`) follow the
  `PlaceReservation` pattern exactly: `[ReadModel][FromEvent<TEvent>] record Existing<X>(TKey Key)`
  injected as a nullable `Handle()` parameter, `is null` ⇒ "doesn't exist yet". For a rule needing an
  *accumulated* set keyed the same way (e.g. "employee already assigned to this shift" — is EmployeeId
  in the set of EmployeeIds already assigned to ShiftId), define a second `[ReadModel]` with a custom
  `IReducerFor<T>` that folds the list (`(current ?? new(key, [])) with { Items = [..current?.Items ?? [], @event.Item] }`)
  and inject it alongside the existence check; `Handle()` then does an in-memory `.Contains(...)`.
- `Cratis.Monads.Result<TSuccess,TError>` needs an explicit `using Cratis.Monads;` in
  `CratisApp.Specs` spec files (unlike the main `CratisApp` project, where it resolves with no
  `using` thanks to the Cratis SDK's own implicit global usings) — the Specs project doesn't get
  those transitively through the `ProjectReference`. API: `IsSuccess` (bool), `TryGetResult(out T)`,
  `TryGetError(out TError)` — no `Match`/`AsT0` visible in this SDK version, use the `TryGet*` pair.
- For a command whose Guid-typed field has no dedicated picker/read-model yet (e.g. `employeeId` with
  no Employee roster built), don't force it through a Cratis `*Field` component — those are
  type-checked end-to-end against the command's declared property type (`InputTextField` requires a
  `string` property; a `Guid` property fails to compile). Follow the `BookATable`/`PlaceReservation`
  precedent: Guid-typed fields are supplied via route params + `onBeforeExecute` (`command.x =
  Guid.parse(...)`), or — when there's truly no context to source it from yet — a plain (non-Cratis)
  PrimeReact input bound to local `useState`, read inside `onBeforeExecute`. `CommandDialog`/`CommandForm`
  happily render arbitrary non-field children as-is alongside typed fields.
- A slice needing per-entity context that no list/detail page exists for yet (e.g. "Assign Employee to
  Shift" needs a `shiftId`, but the shift-listing slices are still Planned) can extend the feature's
  existing composition page with an *optional* route param (`useParams<{ shiftId?: string }>()`) rather
  than inventing a second per-slice page — same precedent as `Booking.tsx` being mapped directly at
  `/restaurants/:restaurantId/book` with no restaurant-list page existing either.
